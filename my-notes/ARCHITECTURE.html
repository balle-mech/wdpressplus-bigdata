USCRN データ基盤マップ

このリポジトリの docker-compose.yml が立ち上げるコンテナは、米国の気象観測データ（NOAA の USCRN）を集めて、加工して、集計して、グラフにするまでの流れを分担しています。どのコンテナが何を持ち、誰と話しているのかを、設定ファイルの中身から図にしました。

左上から右下へデータが流れます。四角をクリックすると、そのコンテナの役割と接続先が下に出ます。

メタデータ

Hive Metastore

もう一度同じ四角をクリックすると、強調表示を解除します。

本に出てくる 3 つの層との対応

DATA LAKE

MinIO の datalake バケット

ダウンロードしたテキストファイルを加工せずに置く場所です。形式はバラバラでよく、とにかく貯めておきます。

DATA WAREHOUSE

warehouse バケット ＋ Metastore

Spark が列の決まった Parquet に変換したもの。ファイル（MinIO）と、その定義（Metastore）の 2 つがそろって初めて SQL で引ける「テーブル」になります。

DATA MART

PostgreSQL の datamart

Presto で日ごとの平均気温に集計した小さな表 uscrn_summary。Metabase はここだけを見るので速く表示できます。

MinIO・Metastore・metastore-db の関係

いちばんつまずきやすいところです。図書館にたとえると、役割の分担がわかりやすくなります。

書庫の本棚
MinIO
本（データファイル）そのものが並んでいる。ただし棚は「どれが何の本か」を説明してくれない。
司書
Hive Metastore
「uscrn という本はどの棚にある？どんな章立て？」に答える窓口。自分では本を運ばない。
目録カードの引き出し
metastore-db
司書が参照する台帳。司書（Metastore）はここに書き込んだり読んだりするだけで、中身はただの PostgreSQL の表。
利用者
Spark / Presto
司書に場所を聞いてから、自分で書庫に行って本を読む（または新しい本を置いて目録に登録してもらう）。
MinIO の warehouse バケットにあるもの
warehouse/
└── uscrn/
    └── year=2020/
        ├── part-00000-….snappy.parquet
        └── part-00001-….snappy.parquet

ただのファイルの集まりです。「これは uscrn というテーブルで、year で分割されている」という情報はどこにも登録されていません。

metastore-db（PostgreSQL）にあるもの
-- Hive が作る管理用テーブル（抜粋）
DBS         default → s3a://warehouse/
TBLS        uscrn
SDS         LOCATION = s3a://warehouse/uscrn
COLUMNS_V2  timestamp  timestamp
            wbanno     string
            temperature double
PARTITIONS  year=2020

テーブル名・列・型・ファイルの場所・パーティション一覧という「データについてのデータ」です。気温の値そのものは 1 件も入っていません。

ポイント: Metastore は「データを通す」コンテナではありません。Presto も Spark も、Metastore からは場所と列の情報だけを受け取り、データ本体は MinIO と直接やり取りします。だから Metastore の設定ファイルにも MinIO の接続先（fs.s3a.endpoint）が書かれていますが、主な用途はテーブルの保存場所（s3a://warehouse/）を扱うことです。

SELECT が実行されるとき

scripts/datamart.py が Presto に集計クエリを投げたとき、コンテナの間で起きることを順番に追います。

SELECT date_trunc('day', timestamp) time, wbanno, avg(temperature) avg_temperature
FROM uscrn GROUP BY 1, 2
  1. datamart.py → presto-server:8080Python（pyhive）が SQL を Presto に送ります。
  2. Presto → metastore:9083（Thrift）「uscrn ってどこにあって、どんな列があるの？」と問い合わせます。Presto 自身はテーブルの定義を持っていません。
  3. Metastore → metastore-db:5432（JDBC）Metastore が PostgreSQL の TBLS や SDS を検索し、「s3a://warehouse/uscrn にある Parquet で、列はこの 3 つ、パーティションは year=2020」と Presto に返します。
  4. Presto → minio:9000（S3 API）教わった場所の Parquet ファイルを MinIO から直接読み込み、日ごとに平均を計算します。
  5. datamart.py → datamart:5432結果を受け取った Python が PostgreSQL の datamart に uscrn_summary テーブルとして書き込み、Metabase がそれをグラフにします。

テーブルを作る側（Spark の saveAsTable('uscrn')）も同じ構図で、Parquet ファイルは MinIO に書き、テーブル定義は Metastore 経由で metastore-db に登録します。

PostgreSQL が 2 つある理由

どちらも postgres:11 イメージですが、役割はまったく別です。同じ製品を別々の目的に使っているだけです。

metastore-dbdatamart
中身テーブル定義（メタデータ）集計済みのデータ（uscrn_summary）
書き込むのはHive Metastore だけdatamart.py
読むのはHive Metastore だけMetabase（人間の分析者）
人が直接 SQL を打つか普通は打たない打つ・グラフにする
初期化docker-compose run --rm metastore /initSchema で約 1200 行の DDL を流して管理用テーブルを作る不要（to_sql が自動でテーブルを作る）

接続先はどこに書いてあるか

コンテナ同士は docker-compose.yml のサービス名（minio、metastore など）をホスト名として呼び合います。Docker が同じネットワーク内で名前解決してくれるためです。Mac から localhost で届くのは、ports: で公開している minio:9000 と metabase:13000 だけです。

起動する順番とその理由

README の手順は、依存される側から先に立ち上げる順になっています。

  1. docker-compose up -d minioデータの置き場。ほかの全員が参照するので最初に起動します。バケット（datalake・warehouse）もここで作っておきます。
  2. docker-compose up -d metastore-dbMetastore が使う台帳用の PostgreSQL。この時点ではまだ空です。
  3. docker-compose run --rm metastore /initSchemaHive の schematool で、metastore-db に TBLS や SDS などの管理用テーブルを作ります。最初の 1 回だけ必要です。
  4. docker-compose up -d metastore台帳が準備できたので、司書役を起動します（depends_on で metastore-db と minio を指定済み）。
  5. docker-compose up -d presto-server起動時に Metastore へつなぐため、Metastore の後に起動します。
  6. docker-compose up -d datamart → metabase出口側。集計結果の置き場と、それを見るツールです。

Spark（spark-submit）と Python は常駐しません。docker-compose run --rm spark-submit … のように、処理を 1 回実行して終わるコンテナです。
